                   ARKHE Chain Format, Version 1
                        (arkhe-chain-v1)

Status of This Memo

   This memo describes a tentative format for append-only cryptographic
   chains of certified hashes.  It is not a standard.  It is a proposal.
   Very little of what is here is firm and reactions are expected.

1. Motivation

   The internet has no owner because its protocols are public.  ARKHE
   ZERO inherits that principle: the format of a chain must be public,
   the key that signs it must not.

   This document defines the smallest possible format for an append-only
   chain of SHA-256 hashes, signed with a detached GPG signature.  Any
   party can create a chain, sign it with their own key, and have it
   verified by any compliant verifier without asking permission from the
   author of this memo.

2. Format

   A chain is a file with one JSON object per line, UTF-8 encoded, LF
   line endings.  The file SHOULD be called chain.log.  Its detached,
   ASCII-armored GPG signature lives alongside as chain.log.asc.

   Each line MUST contain at least the following fields:

     v           integer    format version; MUST be 1
     seq         integer    sequence number; starts at 1, increments by 1
     sha256      string     64 lowercase hex; SHA-256 of the payload
     prev_hash   string     64 lowercase hex; previous chain_hash
     chain_hash  string     64 lowercase hex; sha256(prev_hash || sha256)
     ts          string     ISO 8601 UTC timestamp

   The first line is the genesis entry.  Its prev_hash MUST be 64 zeros
   ('0' * 64).

   chain_hash is computed as follows:

     chain_hash = sha256_hex(prev_hash || sha256)

   where || is string concatenation of the two 64-char lowercase hex
   strings, and sha256_hex(x) is the lowercase hex digest of the UTF-8
   encoding of x.

3. Optional Fields (The Spare Bits)

   The following fields MAY appear.  Verifiers MUST ignore fields they
   do not understand, except fields beginning with "x-", which MUST
   always be ignored (reserved for experimental use).

     id            string    opaque identifier chosen by issuer
     lead_id       string    deprecated alias for id
     payload_type  string    MIME or custom type of the payload
     issuer_key    string    GPG fingerprint of the chain signer
     prev_chain    string    64 hex; parent chain's last chain_hash
     sello_file    string    implementation hint: payload filename
     sig_file      string    implementation hint: signature filename
     x-*           any       experimental; ignored

4. Verification

   A verifier MUST, in order:

   a. Verify the detached GPG signature of chain.log against chain.log.asc
   b. Parse each line as JSON; abort on any parse error
   c. For each entry E at position i (1-based):
      - assert E.v == 1
      - assert E.seq == i
      - assert len(E.sha256) == 64 and len(E.prev_hash) == 64
      - assert E.chain_hash == sha256_hex(E.prev_hash || E.sha256)
      - assert E.prev_hash == previous.chain_hash, or 64 zeros if i == 1
   d. Optionally, for each entry, fetch the payload, hash it, and assert
      that hash equals E.sha256

   A chain that passes (a)-(c) is "chain-valid".  A chain that also
   passes (d) is "payload-valid".  The distinction matters: a chain can
   be signed with a valid key while the payload has been withheld.

5. Multiple Chains

   There is no global registry.  Each chain is a file.  Each chain is
   signed by its own key.  A verifier accepts any chain that passes
   section 4.  Two chains MAY reference each other via prev_chain, but
   this is optional.

   The format is the protocol.  The key is not.

6. Open Questions

   1. Should chain_hash include ts?  This memo proposes it should NOT,
      so a verifier can recompute the chain without trusting any
      timestamp.
   2. How should a chain signal that it has been superseded by another?
      prev_chain was proposed, but its semantics are not defined.
   3. Should the file name be canonical?  This memo proposes chain.log
      but accepts anything ending in .log.
   4. Should there be a signature on each line, or only on the file?
      This memo proposes file-level signing only, because per-line
      signing is expensive and does not add security beyond the chain.

7. Security Considerations

   The format only guarantees integrity and append-only-ness.  It does
   not guarantee that the payload exists, that the issuer is who they
   claim to be, or that the timestamp reflects reality.  Those are
   matters of key distribution and external trust, not of the format.
